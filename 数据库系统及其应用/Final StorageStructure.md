**优势和特点：**
- 记录位置和大小的简介管理
	记录的真实物理位置（在数据区）和大小存储在**槽目录**中，而不是固定在某个地方。
	这是该结构最核心的优势，使得记录可以在页内**自由移动**
- 记录移动和空间的紧凑化
	当记录被**删除**时，会在数据区留下“空洞”（碎片），DBMS可以移动其他记录覆盖
	只需要更新槽目录中的location就行
	减少了内部碎片，提高了空间利用率，移动成本较低
- 指针的稳定性
	外部（例如索引、其他记录）指向页内记录的指针，**不应该直接指向记录在数据区的物理地址**。
- 插入，删除，查找高效。

- 分解为小块，存储在不同的分离的元组中

## 文件中记录的组织
### 记录的组织
1. **堆文件组织 (Heap File Organization)**
    - **核心思想：** 记录可以存放在文件中的**任何有可用空间的位置**。没有强制的物理顺序。
    - **工作方式：**
        - 新记录被插入到文件中第一个有足够空闲空间的 **块（页）** 中。这通常由一个记录空闲空间信息的结构（如空闲空间映射表）管理。
        - 删除记录时，其占用的空间被标记为空闲，可供后续插入使用。
        - 更新记录时，如果新记录长度不超过原记录，则原地更新；如果更长，可能需要移动到更大的空间（类似删除再插入）。
    - **优点:**
        - **插入极快：** 只需找到有空间的页即可插入，通常O(1)或O(少量页)复杂度。
        - **简单：** 实现和管理相对简单。
    - **缺点:**
        - **查询效率低（尤其范围查询/全表扫描）：** 记录物理位置无序，查找特定记录或按顺序扫描记录需要遍历整个文件（或大部分文件）。
        - **空间碎片化：** 频繁的插入和删除可能导致存储空间碎片化（页内有空洞，页间分布不均），降低空间利用率和I/O效率。
    - **适用场景：** 插入密集型负载、对顺序访问要求极低的场景、临时表、日志文件等。

使用自由空间图：对关系中的每个块都包含一个项，每个项表示一个比例f，表示在这个块中有f比例是自由的
对于大型文件，可以使用多级的自由空间图。用一个项代表一百个项，值为100项中空间的最大值f。

2. **顺序文件组织 (Sequential File Organization)**
    - **核心思想：** 记录按照某个**搜索键（Search Key）** 的值（如员工ID、订单日期）进行**物理排序**后存储在文件中。
    - **工作方式：**
        - 记录在文件（块）中严格按照搜索键值的升序或降序连续存储。
        - 插入新记录时，必须找到其在排序序列中的正确位置。这通常需要：
            - 定位到应插入的块。
            - 如果该块有空间，插入记录并移动块内后续记录（保持块内有序）。
            - 如果该块已满，可能发生**溢出（Overflow）**：
                - 将部分记录移到一个单独的==**溢出块（Overflow Block）**== 中。
                - 或者分裂该块（需要重组文件）。
        - 删除记录会留下空隙，需要后续处理（如标记或重组）以避免碎片。
    - **优点:**
        - **范围查询/顺序扫描高效：** 对于在搜索键上的范围查询（如 `WHERE date BETWEEN '2023-01-01' AND '2023-01-31'`）或需要按该键排序输出的查询，可以高效地按物理顺序读取连续的块，I/O效率高。
        - **基于排序键的查找较快（二分查找）：** 可以在文件级别（如果块数不多）或块内使用二分查找定位记录。
    - **缺点:**
        - **插入/删除代价高昂：** 维护物理顺序的成本很高，特别是插入到中间位置时，需要移动大量记录或管理溢出块。频繁插入可能导致性能严重下降和溢出链管理复杂。
        - **空间浪费：** 溢出块和删除留下的空隙会造成空间浪费。
        - **仅对排序键高效：** 对非排序键的查询效率通常很低，接近堆文件。
    - **适用场景：** 数据相对静态、主要基于排序键进行大量范围查询或全表顺序扫描的场景（如历史数据分析、报表生成）。现代数据库较少使用纯顺序文件，其思想更多被B+树吸收。

按照某个搜索键（Search Key） 的值来排序
删除：使用一个指针链表
插入：按照顺序插入
	有空间：直接插入
	无空间：加入一个溢出块
	指针链表需要更新

3. **多表聚簇文件组织 (Multitable Clustering File Organization)**
    - **核心思想：** **打破关系边界**，将经常一起访问的**多个相关表**（如 `Customers` 和 他们的 `Orders`）的记录**混合存储**在同一个物理文件/块中。
    - **工作方式：**
        - 基于预定义的关联关系（如外键 `Orders.customer_id = Customers.id`）。
        - 一个“父”记录（如一个 `Customer`）后面紧跟着存储其所有相关的“子”记录（如该 `Customer` 的所有 `Orders`）。
        - 在块级别，一个块可能包含：
            - 一个父记录及其所有子记录。
            - 或者多个父记录以及它们各自的子记录（如果子记录数量不多）。
    - **优点:**
        - **连接查询性能显著提升：** 这是最主要的动机。当查询需要连接这些相关表时（如 `SELECT * FROM Customers JOIN Orders ON ...`），DBMS只需读取**少量块**就能获取一个父记录及其所有子记录，避免了大量的随机I/O（否则需要根据连接条件在多个表中跳转查找）。
        - **预取（Prefetching）效率高：** 读取一个父记录时，其子记录很可能在同一块或相邻块，可以被预读到内存。
    - **缺点:**
        - **插入/更新/删除更复杂：** 插入新的子记录需要找到其父记录所在的块（或附近有空间的块）。更新父记录的主键或删除父记录会级联影响所有子记录的存储位置。管理存储空间更复杂。
        - **可能降低单表扫描效率：** 如果只扫描其中一个表（如只查 `Orders`），DBMS必须读取混合了其他表记录的块，浪费了I/O带宽（读取了不需要的 `Customers` 数据）。
        - **设计决策关键：** 聚簇哪些表、基于哪个连接关系需要仔细权衡查询模式，设计不当可能适得其反。
        - **空间可能浪费：** 如果父记录没有子记录，或者子记录数量远小于块大小，空间利用率可能不高。
    - **适用场景：** 存在**强关联关系**且**频繁进行等值连接（特别是主外键连接）** 的表对（如 `Customer-Order`, `Order-OrderDetail`, `Department-Employee`）。对于OLTP系统中核心的事务路径非常有效。

4. **B+树文件组织 (B+-tree File Organization)**
    - **核心思想：** 利用**B+树索引结构**本身来**直接组织和存储数据记录**。数据记录就存储在B+树的**叶子节点**中。
    - **工作方式：**
        - 整个文件就是一棵B+树。
        - **非叶子节点：** 存储索引项（键值 + 指向子节点的指针）。
        - **叶子节点：** 存储**实际的数据记录**（或指向实际数据记录的指针，但图片指的组织方式是存储记录本身），并且所有叶子节点按索引键值**排序并通过指针相互链接**。
        - **插入/删除：** 按照标准B+树的插入删除算法进行。当叶子节点分裂或合并时，其中的记录会被物理移动或重新分布。
    - **优点:**
        - **高效的有序访问：** 叶子节点链表使得基于索引键的范围查询极其高效（顺序I/O）。
        - **高效的等值查询：** 通过索引树快速定位记录（O(log n)复杂度）。
        - **动态平衡：** 插入和删除操作会自动调整树结构以保持平衡，确保查询效率稳定。避免了纯顺序文件的插入瓶颈。
        - **高扇出：** B+树节点通常设计为与磁盘块大小匹配，一次I/O能读取很多索引项或记录，减少树高度和I/O次数。
    - **缺点:**
        - **存储开销：** B+树结构本身（非叶子节点）需要额外的存储空间。
        - **插入/删除开销：** 虽然自动平衡，但节点分裂和合并操作本身也有代价（读写多个块）。
        - **可能的空间浪费：** 节点分裂时通常不会填满到100%，存在一定的内部碎片。
    - **适用场景：** **极其广泛**，是关系型数据库中最主流的文件组织方式之一（尤其作为主键组织方式）。特别适用于需要高效点查、范围查询、排序的场景。MySQL InnoDB的主键索引（聚簇索引）就是典型的B+树文件组织。
        
5. **散列文件组织 (Hashing File Organization)**
    - **核心思想：** 使用一个**散列函数（Hash Function）** 作用于记录的**搜索键（Hash Key）** 上，计算出的**散列值（Hash Value）** 直接决定该记录应该存储在文件的**哪个块（桶，Bucket）** 中。
    - **工作方式：**
        - 文件被划分为固定数量的**桶（Buckets）**（通常对应物理块）。
        - 每个桶有一个唯一的桶号。
        - 插入记录时：
            - 计算其搜索键的哈希值 `h`。
            - 根据 `h`（通常取模运算 `h % N_buckets`）确定目标桶号。
            - 将记录放入该桶对应的块中。
        - 查找记录时：
            - 计算搜索键的哈希值 `h`。
            - 定位到桶 `h % N_buckets`。
            - **在桶内搜索**目标记录（可能需要扫描整个桶）。
        - 如果桶满了（哈希冲突），处理方式有多种：
            - **链式法（溢出块）：** 为满的桶链接一个或多个**溢出块（Overflow Block）**，新记录放入溢出块。
            - **开放寻址：** 在数据库文件组织中较少用，因为涉及跨块查找。
    - **优点:**
        - **等值查询极快（理想情况下）：** 如果哈希函数均匀且桶足够大，通常只需**一次I/O**（读取目标桶所在的块）就能找到记录（或确定不存在）。复杂度接近O(1)。
    - **缺点:**
        - **不支持范围查询：** 哈希函数破坏了键值的顺序性，范围查询（如 `WHERE age > 30`）需要扫描**所有桶**，效率极低。
        - **哈希冲突与溢出：** 不均匀的哈希函数或数据分布会导致某些桶溢出，链式溢出会降低查询效率（需要在链上扫描）。
        - **动态扩展困难：** 固定桶数（静态散列）在数据量增长时性能会严重下降（桶溢出链过长）。动态散列（可扩展散列、线性散列）可以解决但增加了复杂度。
        - **空间利用率：** 可能因预留空间或溢出块而浪费。
        - **对键值分布敏感：** 性能高度依赖哈希函数的质量和数据的分布。
    - **适用场景：** 主要用于**等值查询（点查）** 极其频繁且**几乎不需要范围查询**的场景。例如：基于主键的快速查找、内存数据库的存储结构、连接操作的哈希连接实现、某些缓存系统。现代数据库通常将其作为**辅助存取路径（哈希索引）** 而非主文件组织方式。

## 数据库缓冲区：
需要减少块在内存和磁盘上的交换
- Buffer：主存中用于存储磁盘块拷贝的部分
- Buffermanager：负责缓冲区资源的分配

### Buffermanager
1. **固定块（Pinned Block）**
    - **操作流程**：
        - 读/写块前调用 `pin()`：锁定块防止被置换，`pin_count++`
        - 操作完成后调用 `unpin()`：`pin_count--`，若为0则允许置换
    - **并发控制**：
        - 多个事务可同时固定同一块（`pin_count` 计数）
        - 仅当 `pin_count=0` 时，缓冲区管理器可将其淘汰

2. **缓冲区锁协议**
    **共享锁 (S)** 允许多事务并发读取块内容 与排他锁互斥；多个S锁可共存
    **排他锁 (X)** 独占块进行修改（如重组记录） 与所有锁互斥；同一时刻仅一个
    - **典型场景**：
        - 移动块内记录时需加X锁（防止其他事务读取不一致状态）
        - 查询时加S锁（允许并行读，但阻塞X锁请求）

### 缓冲区替换策略
#### LRU
- 使用之前的部分来推测接下来的情况
- 有时候效果不好
```
          for each tuple tr of r do  
            for each tuple ts of s do  
              if the tuples tr and ts match …
```
- 当缓存满时，LRU优先淘汰**最久未使用的B1**，但后续循环需**重新加载B1**（反复I/O）

#### 立即丢弃策略
一旦元组处理完毕，就会释放这个块

#### MRU最近最常使用策略
当前处理块解固定后标记为"最新"，置换时优先保留

#### 优化器提示混合策略
查询优化器根据访问模式提示缓存策略

## 面向列的存储：
关系中的每个属性都单独存储
#### **优点**
1. **减少 I/O 操作**：仅需读取查询涉及的列，而非整行数据。
2. **提升 CPU 缓存效率**：连续存储的列数据更符合 CPU 缓存局部性原理。
3. **更高的压缩率**：同列数据通常具有相似性（如数值、重复字符串），压缩效果更佳。
4. **支持现代 CPU 向量化处理**：列式数据便于 SIMD（单指令多数据）并行计算。
#### **缺点**
1. **行重构开销**：从不同列重建完整元组需要额外计算。
2. **删除和更新成本高**：需跨多列修改数据，可能影响压缩效率。
3. **解压缩开销**：读取压缩列需先解压，增加 CPU 负载。
#### **适用场景对比**
- **列式存储**：更适合决策支持系统（OLAP），如大数据分析、聚合查询。
- **行式存储**：更适合事务处理（OLTP），如高频增删改操作。
- **混合存储（Hybrid）**：部分数据库同时支持两种存储，灵活适配不同负载。
