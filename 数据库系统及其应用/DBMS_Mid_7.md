# 关系数据库设计

### 1.好的关系设计的特点
问题：冗余，增删查改上的问题
#### 分解
- **有损分解**：分解过程中有信息的损失
- **无损分解**：分解过程中没有信息的损失

#### 无损分解
**定义**：R为关系模式，R1和R2为R的分解，R=R1 U R2，如果R1和R2区代替R时没有信息的丢失，就称其为**无损分解**
```sql
 select* from 
	 (select RI from r) 
	 natural join 
	 (select R2 from r)
```

#### 规范化理论
用于设计关系数据库的方法时使用一个称作**规范化**的过程。目标是生成一组关系，避免冗余和轻松检索信息。
- 确定一个给定的关系模式是否为”良构的“
- 如果不良构，则无损分解为较小的关系模式，使得每个模式都满足适当的范式。

#### 无损分解和函数依赖
使用函数依赖来说明分解是否无损：
- R1 n R2 -> R1
- R1 n R2 -> R2
也就是说，R1R2的交集要么构成R1要么构成R2的超码，那么就是一个无损分解。
**可以使用属性闭包来高效的检验超码**
假设r(R)分解为r(R1)和r(R2)，其中R1 n R2 —>R1/R2,那么必须对分解后的模式施加SQL约束以确保内容和原始内容一致
- R1 n R2 是 r1的主码。（磁约束强制实施函数依赖性）
- R1 n R2 是从 r2 引用的 r1 的外码（确保匹配元组）

#### BCNF
基本消除了基于函数依赖所能发现的冗余（对于3NF消除了主属性内部的部分和传递依赖）
1. 定义：
	对于函数依赖集F的关系模式R属于BCNF的条件是，对于F+中的所有形如X->Y的函数依赖，至少有一条成立：
	- 是平凡函数依赖
	- X是R的一个超码
	分解规则：
	使用以下两个模式区代替R
	- （X U Y）
	- （R-（Y-X））
	- 然后将不符合BCNF的继续分解
	
2. BCNF和保持依赖
	约束复习：主码，函数依赖，check，断言，触发器...[[DBMS_Mid_4]]
	检查约束时开销很大。需要高效检查约束的方式来设计数据库。
	到BCNF的分解会妨碍对特定函数依赖的高效检查
	- （可以验证只包含两个属性的模式都属于BCNF）
	分解后的BCNF可能会出现这样的问题：没有一个模式包含出现在函数依赖中的所有的属性，需要通过计算分解后的关系的连接来检查。
	由于我们的设计不允许没有链接的情况下强制实施这种函数依赖，所以是非保持依赖。

#### 第三范式 3NF
非主属性对主属性没有传递函数依赖
允许左侧不是超码的特定非平凡函数依赖
条件是：对于F+中所有X—>Y的函数依赖，至少有一条成立
- 是一个平凡的函数依赖
- X是一个超码
- Y-X中的每一个属性A都被包含于R的一个候选码中。（也就是说，Y-X中的所有属性都是主属性）

#### BCNF和3NF的比较
3NF：
- 优点：不牺牲无损性和保持依赖性
- 缺点：不得不使用null表示联系，存在信息重复问题
数据库设计目标：
- BCNF
- 无损性
- 保持依赖性

### 使用函数依赖的分解算法。
#### BCNF分解：
BCNF的定义可以用于检查一个关系是否属于BCNF，但是计算闭包很繁重。
检测：
- 为了检查一个非平凡的依赖α—>β是否违反BCNF，可以计算α的闭包，并且验证是否包含R的所有属性（是否为R的一个超码）
- 检查一个R是否违反BCNF，只需要检查给定的集合F是否违反BCNF，不必检查F+
- 但是R分解后，检查F的方法不可用。
- 代替方法：对于Ri中的每一个子集α，检查α的闭包+，要么不包含Ri-α的任何属性，要么包含Ri的所有属性，如果有一个α违法了条件，则违反了BCNF
