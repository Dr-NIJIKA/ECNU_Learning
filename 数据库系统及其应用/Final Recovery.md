## Undo机制

Undo是指**撤销未完成或中止事务的影响**的过程。它的核心特点是：

- 确保事务中止时**没有任何部分更改是持久的**
    
- 主要处理事务执行过程中产生的中间状态
    
- 是原子性(Atomicity)的重要保障
    

## Redo机制

Redo是指**重新应用已提交事务的效果以实现持久性**的过程。它的核心特点是：

- 确保**一旦DBMS通知用户事务已提交，该事务的所有更改必须是持久的**
    
- 主要处理系统崩溃后恢复已提交但未完全持久化的事务
    
- 是持久性(Durability)的重要保障

## Steal与No-Steal策略

### Steal策略（偷取策略）

**定义**：允许==**未提交事务**==的修改页被"偷取"写入磁盘（即使事务还未提交）==修改非易失性存储器上的对象的值==

**特点**：

- 高并发性：缓冲池空间紧张时，可以立即置换脏页（包含未提交修改的页）
    
- 需要Undo日志：因为未提交的修改可能已写入磁盘，回滚时需要撤销这些修改
    
- 典型实现：大多数现代DBMS采用此策略（如MySQL、PostgreSQL）
    

**示例**：

事务T修改了页A(1→3)，但未提交
此时若缓冲池需要空间，允许将A=3写入磁盘
若T最终回滚，需要通过Undo日志将A恢复为1

### No-Steal策略（非偷取策略）

**定义**：禁止未提交事务的修改页被写入磁盘

**特点**：

- 简单恢复：无需担心磁盘上有未提交数据
    
- 内存压力大：必须保留所有未提交事务的修改页在内存中
    
- 较少使用：限制了系统并发性能
    

**示例**：

事务T修改了页A(1→3)，未提交前
即使缓冲池空间不足，也不允许A=3写入磁盘

## Force与No-Force策略

### Force策略（强制策略）

**定义**：事务**提交前**必须将其所有修改页立即写入磁盘

**特点**：

- 强持久性：确保提交后数据立即持久化
    
- 性能开销：每次提交都伴随大量磁盘I/O
    
- 无需Redo日志：因为提交数据已全部在磁盘上
    

**示例**：

事务T修改了A(1→3)和B(2→4)
提交时，必须确保A=3和B=4都写入磁盘后才返回成功

### No-Force策略（非强制策略）

**定义**：允许提交事务的修改页保留==在内存中==不立即写入磁盘

**特点**：

- 高性能：减少提交时的磁盘I/O
    
- 需要Redo日志：崩溃后需要重做已提交但未持久化的修改
    
- 现代DBMS普遍采用：如Oracle、SQL Server等
    

**示例**：

事务T提交后，A=3和B=4可能仍留在内存
系统定期通过checkpoint或后台线程写入磁盘
若崩溃，通过Redo日志恢复这些修改

## 影子分页
Shadow Paging 是一种**基于副本切换的恢复技术**
保持数据库的两份拷贝
- **Master（主副本）**：仅包含**已提交事务**的修改
- **Shadow（影子副本）**：存储**未提交事务**的所有临时修改
- **原子切换**：事务提交时，通过原子操作将Shadow提升为Master

txn只在影子副本上进行更新，事务提交时，通过原子操作将Shadow提升为Master
（切换指针讲Shadow变为Master，再释放掉旧的master）
他的缓冲池策略为：
NOSTEAL+FORCE

优缺点：
- 简单地实现了回滚和恢复
	Undo：删除shadowpage，其他不变
	Redo：不需要Redo：已完成的永久有效，未完成的没进入过disk
- 复制整张页表开销昂贵
	B+树
	不需要复制整张树，只需要复制路径，修改叶子节点
- 提交的开销大

Log-Based Recovery
WAL：Write-Ahead Logging    预写日志
是一种用于保证数据库系统中数据操作的原子性和持久性的重要技术。WAL 的核心思想是：**先写日志再写数据文件**，即所有的修改在提交之前都要先写入日志文件中。

Buffer Pool Policy: **==ESTEAL + NO-FORC==**
![[Pasted image 20250614154933.png]]
 **WAL协议核心规则**
1. **写入顺序强制**：
    - 修改数据页前，其对应的**日志记录必须已持久化**
    - 事务提交前，**所有日志记录必须持久化**

2. **日志内容要求**：

| 日志类型         | 内容                | 目的      |
| ------------ | ----------------- | ------- |
| **Undo记录**   | `<T,X,old_value>` | 回滚未提交事务 |
| **Redo记录**   | `<T,X,new_value>` | 重做已提交事务 |
| **Commit记录** | `<T,COMMIT>`      | 标记事务完成  |

图中提示"Find the buffer when it is full"，表明：
- ==**触发机制**：日志缓冲区满时触发批量写入==
- **备选机制**：定时器超时或提交事务数阈值


## 崩溃恢复三阶段
### 阶段1：分析阶段

1. 扫描日志确定：
    
    - **重做起点**：最近检查点位置
    - **需Redo事务**：检查点后提交的事务(T2)
    - **需Undo事务**：崩溃时活跃的事务(T3)
        
### 阶段2：重做阶段(Redo)

- **重做对象**：所有**已提交事务**的修改
    
- **执行逻辑**：
        
    for lsn in checkpoint_lsn to end_log:
        if lsn is DATA_MODIFICATION and txn COMMITTED:
            redo(lsn)  # 无条件重做
    
- **示例**：即使数据页已更新，也重新应用修改（幂等操作）
    
### 阶段3：撤销阶段(Undo)

- **撤销对象**：所有**未提交事务**的修改
    
- **执行逻辑**：
    
    for txn in active_txns:        # 按LSN倒序
        while txn_logs:
            lsn = last_log_of(txn)
            undo(lsn)              # 反向撤销
            write <T, ABORT> log   # 记录撤销

Log计划：
物理日志 ：在数据库内记录change
逻辑日志 ：通过事务的执行来记录

## 检查点
- Output onto stable storage all log records  将当前位于主存的所有日志记录输出到稳定存储器
- Output to the disk all modified data blocks  修改的缓冲块输出到磁盘
- Write a  ==CHECKPOINT ==entry to the log and flush to stable storage.

问题：
 - **DBMS 执行检查点时必须暂停事务，以确保获得一致性快照**
 - **扫描日志以定位未提交事务可能耗时极长**
 - **难以确定 DBMS 应多久执行一次检查点**
	**检查点过频 → 运行时性能下降。系统消耗过多时间刷写缓冲池**
	**但间隔过长同样有害 → 检查点过大且缓慢，导致恢复时间灾难性延长**
